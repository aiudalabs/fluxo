Fluxo · arquitectura fundacional · docs/19

La fábrica no genera código.
Orquesta devs que corren la app.

Fluxo tiene todo lo que necesita — Claude Code, BMAD, el sustrato. La falla no fue construir un dev peor. Fue poner al mismo Claude en una caja que no lo deja buildear ni correr lo que hace.

Tesis: Fluxo es un orquestador. No desarrolla ni revisa. Coordina devs = Claude Code en una máquina de dev real y reviewers = Claude Code de contexto fresco, ejecutando BMAD (el método, ya en registry/). No reinventamos: ensamblamos y le sacamos los handicaps al dev.

El insight

El dev de Fluxo ya es Claude Code

Literal. El runner del engine corre el mismo binario que corrés en tu compu — en modo headless:

# scripts/agent-runner.sh
docker run --user 1000:1000 -v "$WD:/work" fluxo-agent:local \
  claude -p --output-format stream-json --model "$MODEL" "$PROMPT"

No hay que enseñarle a trabajar bien. Hay que dejar de enjaularlo. La caja tiene dos handicaps — los dos generales (web, mobile, desktop, lo que sea):

Handicap 1 · entorno

No es una máquina de dev real

La imagen es node:20-slim + Flutter. Sin Android SDK, sin Xcode, sin browser.

Cuando el mismo Claude intenta flutter build apk, no puede → hace flutter test (VM Dart). En tu compu el SDK está y buildea. Ese es el bug del APK, palabra por palabra.

Handicap 2 · mandato

Apunta a los tests, no al artefacto

El prompt dice literal: "implementá y corré los tests… commiteá con los tests en verde".

Dice tests, no "buildeá y corré la app hasta que ande". El agente optimiza el gate, y el gate mide el proxy equivocado. Salonara (web) salió con UI pobre por lo mismo: nunca la corrió ni la miró.

Resultado: el agente finge — google-services.json falso, android/ sin gradle ni MainActivity, todo "verde". Es el patrón L-BUILD-1: stub certificado como éxito. Nace de medir el proxy equivocado.

La arquitectura objetivo

Tres roles. Dos agentes (juicio), uno orquestador (determinista).

Realinea a Fluxo con su propia tesis: cero metodología en código · agente donde hace falta juicio · el sustrato se alquila.

Agente · juicio

El DEV

= Claude Code en una máquina de dev real

  • Entorno = imagen con el toolchain común pre-instalado + puerta abierta: si falta algo, el agente lo instala (versión que el repo declara → cero skew). build y run POSIBLES.
  • Mandato = "buildeá y CORRÉ el artefacto; no está hecho hasta que arranca". Como trabajás vos.
  • Anti-stub: falta una credencial → gap declarado (capability), no un config falso.
Agente · juicio

El REVIEWER

= Claude Code de contexto fresco (el rol QA de BMAD)

  • Corre después del sprint, sin las racionalizaciones del dev.
  • Verifica desde cero: ¿buildea? ¿arranca/corre? ¿matchea spec/mockups? ¿hay stubs? ¿cobertura?
  • Sale: findings → stories nuevas con severidad P0 o diferido.
Determinista · sustrato

FLUXO = el ORQUESTADOR

Lo que ya hace, más el re-feed. No cambia de naturaleza.

  • Aislamiento (RLS), identidad, capabilities (Vault, BYO)
  • Máquina de estados + backlog = fuente de verdad
  • Dispatch: story/sprint → dev en la imagen correcta
  • Re-feed: findings P0 → backlog → dev, hasta 0 P0
  • Merge solo de lo que buildea + corre + fue revisado
  • Cero método en código — BMAD vive en registry/

Spec de implementación

Ordenado por leverage — data/config + pegamento fino

F1

Imagen(es) con el toolchain común + puerta abierta a instalar lo que falte

Base buena con lo común pre-instalado (Flutter+SDK; node+browser) — egress cerrado; y si falta algo, el agente lo instala on-demand (versión que el repo declara → cero skew, egress curado). Solo esto ya cazaba el APK roto en SP1.

F2

El mandato build-and-run

Reescribir la NOTA del runner + las personas *-dev.md: "done = buildea y corre", regla anti-stub. Es data (markdown), cero código.

F3

El agente reviewer + su workflow

registry/agents/reviewer.md (contexto fresco, checklist build+run+spec+anti-stub+cobertura) + workflows/review.yaml. El E2E de YoMap ES su checklist.

F4

El re-feed loop

Findings P0 → stories → dispatch a dev → re-review, hasta 0 P0. Reusa backlog + dispatch + la ceremonia sprint-review. Cablear severidad + "sprint done ⟺ 0 P0".

F5

Subordinar el verify harness

test-verify/ui-verify pasan a señal barata; el build+run del reviewer es el gate de calidad real.

TL;DR — Fluxo tiene Claude Code (el dev), BMAD (el método) y el sustrato (aislamiento, estado, dispatch, backlog). Falta: (1) dev = Claude Code en máquina real + mandato build-and-run; (2) reviewer = Claude Code fresco que devuelve findings P0 al backlog; (3) Fluxo orquesta el loop hasta que corre. No es reinventar la rueda — es poner el orquestador arriba de piezas que ya funcionan, y hacer que "done" signifique "corre".
